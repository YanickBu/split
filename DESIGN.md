# Split v4 design brief

Status: design for a future implementation. Split v3 remains the current reference for the UI and Liveblocks sync. This document records product decisions and the tests an implementation must pass.

## Core philosophy

1. **No BS.** The app helps friends split expenses. Every screen and feature must earn its place. A trip should be usable without setup, tutorials, dashboards, or account creation.
2. **No accounts, ever.** A group is shared by a link or QR code. Possession of the group link grants access. The people using it trust one another. The app still protects against accidents, broken data, and leaked infrastructure credentials.
3. **Installable and offline for the whole trip.** Split is a Progressive Web App that users can add to their home screen and open like an app. After a group has been opened once, the app and its data must work without a network for at least a month of normal use, then merge changes when connectivity returns. Adding, viewing, and calculating expenses must never wait for a network request.
4. **Small and fast.** Vanilla HTML, CSS, and JavaScript. No React, Vue, Angular, or mandatory build pipeline. Aim for a 200–500 line *UI layer* if it stays readable. The whole application may need more code for currency data, sync, and tests. Measure transferred bytes, cold load, and operation on a 100 kbit/s connection rather than treating line count as the only target.
5. **Payer-friendly rounding.** Each participant's share is rounded **up** to the smallest unit of the group's currency. The payer receives the resulting rounding difference. This is intentional product policy, not a precision bug.
6. **A ledger that explains the answer.** Expenses and corrections are explicit, replayable records. Balance calculations are deterministic and testable. A display value must be traceable to its source events.
7. **Simple endings.** No global “Settle up” button in the initial v4. Show the suggested transfers; friends settle outside the app and may create a fresh group for the next trip. Add payment recording only if real use shows a need for partial or tracked payments.
8. **Cheap to start, possible to leave.** Keep group records in a documented, exportable format. Service-specific objects stay behind a small storage adapter so the app can move off Liveblocks later.

## What to retain from v3

- The overall visual direction, group links/QR sharing, expense entry, multi-currency support, and local Yjs/IndexedDB persistence.
- Liveblocks as the sync and cloud persistence service **for v4's first release**. There is no AWS backend in the initial implementation.
- An event-based expense history, with edits represented as correction events rather than silent mutation.

## Exact balance rule

Store an expense amount in integer **minor units** of its currency. The group settlement amount is also an integer in the group's currency. A currency's minor-unit exponent must be explicit; do not assume every currency has two decimal places. Parse decimal input exactly and reject values that cannot be represented in that currency's smallest unit. Do not use JavaScript floating-point numbers for ledger arithmetic.

For a positive group amount `A` and `n > 0` distinct participants:

```text
share = ceil(A / n)                 // integer minor units
billed = share * n
rounding_bonus = billed - A         // 0 <= bonus < n minor units
balance[payer] += billed
for each participant: balance[participant] -= share
```

Example: a $10.00 expense split among three people has shares of $3.34. The payer is credited $10.02, including a $0.02 rounding bonus. If the payer is one of the three, their net balance from this expense is +$6.68; the others each have -$3.34. The UI should explain the bonus when showing expense details. The sum of all balances stays exactly zero.

Store the chosen participant IDs on the expense. A group is one trip's ledger: a name, one settlement currency, friends, expenses, and balances. Members may be added later, but removal is allowed only **before the first expense**. Once an expense has been recorded, even if later voided, the removal control disappears. Create a new group for a different roster. Historical participants and their balances are never changed by roster changes.

Foreign-currency expenses store the original amount/currency, group amount/currency, rate source, rate date, and conversion/rounding rule. A rate that is unavailable offline stays unresolved; the app must not silently use a 1:1 or current rate for a historical date. When a rate becomes available, resolution is an explicit event. The specific FX rounding policy needs a focused decision before code is written.

**Unresolved FX is visible.** An expense without a group amount is saved and shown, but excluded from balances and suggested transfers. Label the balance view **Provisional** and show the number and original amounts of excluded expenses next to it. Never display “all settled” while one remains unresolved. The expense detail offers “Enter group amount” so friends can choose an amount manually if the historical rate never arrives. This creates a `RESOLVE_RATE` event with `method: "manual"` and the entered integer group amount. An automatic provider result creates the same event type with `method: "provider"`, provider name, rate date, and exact decimal rate string. Every resolution also carries `revisionId`, `originalAmountMinor`, and `originalCurrency` from the exact expense revision it resolves. Any manual resolution wins over provider resolutions **for that same revision**; among resolutions of the same method the greatest event order wins. Later manual changes are another manual resolution event, never a mutation. Display the method and amount used. The exact rule for converting a provider rate to group minor units must be decided before provider resolution ships; manual resolution works without it.

**Group metadata is ledger data.** Exactly one `CREATE_GROUP` event defines group ID, name, settlement currency, currency exponent, and both the creator's member ID **and display name**. The settlement currency and exponent are locked for that group; create a new group to change them. The name is also fixed in the initial v4. Yjs maps may cache derived values, but a map value cannot override `CREATE_GROUP`. Reject a second, different creation event for the same group.

Required ledger properties:

- Replaying the same valid event set gives the same balances on every device, regardless of arrival order.
- Duplicate delivery of an event changes nothing; each event has a random stable ID.
- Every accepted expense has a positive integer amount and at least one distinct participant.
- The sum of balances is zero in integer minor units after every replay.
- `billed - amount` is the displayed rounding bonus and is in `[0, n - 1]` minor units.
- Corrections, voids, and rate resolutions follow the deterministic event rules below.
- An active-member change never rewrites historical participants or balances.

Do not claim the current short `prevHash` chain proves immutability. Concurrent offline devices can append against the same previous event. Prefer stable event IDs plus deterministic replay and validation. Add cryptographic proofs only if there is a concrete threat they solve.

## Event schema and deterministic replay

Version 1 events are plain JSON records with exactly `schemaVersion`, `groupId`, `id`, `clock`, `type`, and `data`. `id` is a random 128-bit or stronger ID encoded as a string. `clock` is a JSON integer satisfying `0 <= clock <= Number.MAX_SAFE_INTEGER`; reject nonintegers and larger values. On a device, each new event uses `1 + max(clock)` of its known **valid** events. If the maximum is already `Number.MAX_SAFE_INTEGER`, stop with an explicit error rather than wrap or round. `CREATE_GROUP` has clock 0; all other events have clock at least 1. Money minor units are base-10 integer **strings** in event data, parsed with `BigInt`, so large valid amounts do not depend on JavaScript safe-integer limits. `ADD_MEMBER` carries `memberId` and immutable display `name`; participant and payer fields contain stable member IDs, not names. Event types for the initial release are `CREATE_GROUP`, `ADD_MEMBER`, `REMOVE_MEMBER`, `ADD_EXPENSE`, `EDIT_EXPENSE`, `VOID_EXPENSE`, `RESOLVE_RATE`, and the migration-only `LEGACY_OPENING`. Edits carry a **complete replacement expense payload** and `expenseId`; voids and rate resolutions also reference `expenseId`. The payload schema and validation rules are versioned together. Unknown schema versions are retained for export but excluded from calculations with a visible error.

Canonicalize event JSON with sorted object keys and exact string values. For each ID, identical canonical records are one event. If **different** canonical records claim the same ID, quarantine *all* records with that ID, show a conflict, and exclude them from the projection. Arrival order never selects one. Recovery requires exporting the full set and creating a repaired group; v4 does not silently choose a claimant. This also applies to `CREATE_GROUP`; if its ID collides or two different creation records exist for the group, stop the group projection and require repair.

For otherwise valid events, sort by `(clock ascending, id ascending)` using bytewise comparison of IDs. This is the one replay order, independent of Yjs array position, wall-clock timestamps, or arrival order. The creator is declared by `CREATE_GROUP`; the first `ADD_MEMBER` for another member ID fixes its display name, and later additions of that ID with a different name are invalid. An expense's payer and every distinct participant must be declared **and active at the expense's position in replay order**. If an `ADD_MEMBER` has not arrived, keep the expense unresolved and mark totals provisional; once it arrives, replay again. If the member's declaration sorts after the expense, or a valid removal sorts before it, the expense is invalid and excluded with a visible conflict. Arrival order cannot make it valid. Old valid expenses keep their recorded IDs and balances after later membership changes.

The first structurally valid `ADD_EXPENSE` (positive amount and well-formed IDs), including one later voided, locks removals. A `REMOVE_MEMBER` is valid only if its clock is **strictly less** than that first expense's clock; an expense at the same clock wins this tie. If a concurrent earlier removal makes an expense's member inactive, keep the expense as an explicit conflict instead of silently changing its split. An `ADD_MEMBER` may still occur after the lock and affects only later expenses. A migration-only `LEGACY_OPENING` contributes its signed integer balance vector once, before ordinary v4 expenses; its vector must sum to zero and reference members declared in the migration's `CREATE_GROUP`/`ADD_MEMBER` events. It locks removals immediately in a migrated group, even before its first new v4 expense.

For each expense, the greatest `EDIT_EXPENSE` in event order supplies its full payload; concurrent edits with the same clock therefore resolve by ID. The current `revisionId` is the winning edit's event ID, or the original `ADD_EXPENSE` ID if unedited. Keep losing edits in history and show a conflict note in the expense detail. `VOID_EXPENSE` is terminal: if any valid void references the expense, the expense contributes no balance, regardless of edit order. No edit or rate resolution can resurrect it. A `RESOLVE_RATE` applies **only** when its `revisionId`, original amount, and original currency all equal the current revision. Ignore and retain mismatched resolutions in history, even if their clock sorts after the edit; ordering alone never proves what was converted. For an unvoided expense, a valid manual resolution wins over every provider resolution for that revision; otherwise the greatest resolution in event order wins. A complete edit that changes the original amount or currency must clear the group amount for foreign currency and get a new revision-bound resolution. An edit that changes only the title may carry the previously resolved group amount and provenance forward in its complete payload. For same-currency expenses, group amount equals original amount. Test an offline edit and stale provider result with equal clocks and both ID orders. A deliberately high logical clock can win a conflict in this trusted-friends model; the rule guarantees convergence, not fair arbitration.

## Offline and sync behavior

One group corresponds to one Yjs document and Liveblocks room. Group events have a versioned, plain-data schema that can be serialized independently of Yjs. Keep an IndexedDB copy on the device. A service worker caches the HTML, CSS, JavaScript, icons, and other code required to open the app offline. Serve required JavaScript from the app origin instead of depending on a CDN during offline reloads.

Ship a real web app manifest with a name, start URL, standalone display mode, and suitable 192 px and 512 px icons; serve it over HTTPS. The installed icon must open the app and previously opened groups while the device is offline. Offer a discreet “Add to Home Screen” entry where installation is available, then hide it after installation. Chromium's `beforeinstallprompt` can launch its install prompt; on iOS, give short Share-menu instructions because that event is unavailable. Do not show an install banner on every visit. Installation is an app affordance, not a promise that the browser will never evict local data. [PWA installation requirements and browser differences](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable).

V3 already tries to register `split_v3/sw.js` and links `split_v3/manifest.json`, but neither file exists in that directory. V4 must supply both and test their actual URLs. V3's install button alone does not provide a reliable standalone offline app.

On reconnect, open the Liveblocks room and let Yjs merge its document. Rebuild balances from the merged event set and apply the collision rules above. The sync adapter must compare canonical event IDs and contents, not array positions or mutable group-map snapshots. Devices need not be online simultaneously. Check that edits, member changes, and rate resolutions converge as well as simple new expenses.

Do not keep v3's per-event `synced: true` flag. A local Yjs write proves only that the device has stored the event locally. The UI can show a small connection indicator when useful, but must not claim that an individual event reached Liveblocks without a real acknowledgement. The local event list itself is the offline queue; a second custom queue and a permanent badge on every row are unnecessary unless testing proves otherwise.

Browser storage can be evicted or cleared, so “works for a month” is an acceptance target for a retained installation, not an absolute promise after a user clears site data or loses their device. Request persistent storage where supported, detect write failures, provide a small export/import backup, and test the target browsers. [Browser storage behavior](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).

**Fixed release test matrix:** Android Chrome 120+ and iOS Safari 17.4+, each both as an installed home-screen app and as an ordinary browser tab. Also smoke-test current desktop Chromium. “Normal use” means one group starting with five members, at least 100 expenses and 20 edits/voids per device, a later member addition, and an attempted removal after the first expense, with the app opened and used at least weekly. After initial installation and group load, keep the devices without network for **30 actual calendar days**, enter events throughout that period, then reconnect the two devices in both orders and compare canonical event sets and exact balances. Run faster simulated-clock tests during development, but they do not replace the elapsed-time field test. If a target browser cannot pass, report the failed target and narrow the support promise before release.

## Storage adapter contract

`GroupStore` must expose these semantics regardless of provider: `open(groupId)` loads and merges local events before network access; `append(event)` validates and commits locally or returns an explicit storage error; `subscribe(groupId, onChange)` reports canonical event-set changes; `reconcile(groupId)` merges local and remote sets by ID and quarantines differing contents; `export(groupId)` includes every raw event, including invalid, voided, and losing edits; `import(groupId, archive)` validates schema and merges idempotently. Neither reopening nor retrying may create a second copy of an event. If local and remote have different records for one ID, use the collision rule above and retain both for export. The adapter must never silently replace the local set with a remote snapshot.

Yjs itself does not enforce append-only history: a deletion can sync. Before putting an event into Yjs, `append` first commits its canonical record to a separate local IndexedDB event archive. On open and every reconcile, compare the Yjs room, the local archive, and any imported archive; merge by canonical ID/content. If an event present in the local archive is missing remotely, flag the shrink and republish that same event ID. A remote deletion must never delete the local archive entry. Export the union and include quarantined records. If all devices lose their archives and the remote room has lost an event, recovery is impossible without a backup; do not claim absolute immutability. Test remote deletion, local deletion, restart, re-upload, and loss of the last surviving copy.

There are two acknowledgement levels: **local commit** (IndexedDB write completed) and **remote verified** (a read-back from the remote store contains the same ID and canonical content). A Liveblocks connection or Yjs `synced` event alone is not per-event proof of remote durability. `remote verified` may be batched and is not required for expense entry; it must never be claimed before read-back. Keep this state internal unless a user needs recovery information. A future AWS adapter must satisfy the same contract before replacing Liveblocks.

## Trust and sharing

No account, email, password, or identity provider. Generate group IDs with `crypto.getRandomValues`/`crypto.randomUUID`; do not use time plus `Math.random`. Treat the group link as a bearer capability: anyone who has it can read and change the group. Show this plainly when sharing. Never put an AWS or Liveblocks **secret** key in the browser. The current Liveblocks public key is intended for public/prototype access. A copied link cannot be revoked in the first release: the practical response is to export the group, create a new group with a fresh link, and share that link only with the intended friends. **Do not write a migration marker pointing to the new room in the compromised old room:** anyone holding the old link would learn the new capability. The old room remains potentially writable; the UI must not call this a secure revocation. [Liveblocks authentication guidance](https://liveblocks.io/docs/api-reference/authentication).

The first release is an **invited pilot**, not an open public launch. Monitor Liveblocks monthly active rooms, stored bytes, and connection/usage limits in the provider dashboard at least weekly. At 350 monthly active rooms (below the current 500-room free allowance), stop inviting new groups and decide whether to pay or migrate; set a billing alert before enabling overage. A public project key does not prevent arbitrary clients from creating rooms or consuming quota, even with unpredictable group IDs. Before a broad public launch, add a tiny capability-check endpoint that exchanges a secret group link for Liveblocks room access and rate-limits group creation; this uses no accounts. Until that exists, state the quota-abuse risk openly. [Liveblocks free limits](https://liveblocks.io/docs/pricing/plans/free), [Liveblocks authentication guidance](https://liveblocks.io/docs/api-reference/authentication).

Trusted friends still make mistakes. Validate event shapes and money rules on every device before applying them. If a bad event arrives, ignore it in the balance projection and show a recoverable error; do not let one malformed record blank the whole group. Export must preserve the full event history and IDs.

## UI scope

Primary flow: open group → add expense → see balances and suggested transfers. Keep the expense list and edit/void action close to that flow. Put export, group sharing, and member management behind small secondary controls. Remove duplicate hints, novelty badges, analytics, and global settlement controls unless user testing shows a clear need. Keep touch targets and keyboard use practical. Measure compressed app payload and run an offline cold start and a throttled 100 kbit/s load test.

## V3 migration: explicit, reviewed, and once per group

Migration is optional for an existing v3 group; starting a fresh v4 group is the simple path. It is **never automatic** when a device opens an old link. A friend explicitly starts migration while online, after the old Yjs room has fully synced. Ask the group to stop entering v3 expenses at that point. The authoritative source is the complete v3 **Yjs document** (group map and raw event array), not CSV: v3 CSV exports only currently valid expenses and omits voids and edit history. Save a byte-for-byte binary archive of the old Yjs document and its **archive SHA-256 digest** before conversion. That digest verifies the archived bytes only; it is not used to detect later legacy edits. If the source is unavailable or cannot be archived, stop and offer a new group instead.

V3's numbers and names cannot be converted into an exact v4 event history automatically. Preserve the raw v3 document as a read-only legacy archive in the v4 group, within the room-size limit; if too large, stop and offer an external export plus a new group. Build one `LEGACY_OPENING` event containing a zero-sum vector of confirmed balances in v4 minor units and a digest of the source archive. Old expenses remain read-only; new v4 expenses start after the opening balances. Use v3's own balance projection over its stored `groupAmount` values to propose the opening vector, **not** a fresh rate lookup or a reinterpretation of the old expenses under v4's rounding rule: v3 may have used a current rate when the historical lookup failed. For each archived amount, show the stored value, `Number.toString()` decimal representation, and what half-up conversion to group minor units would produce. This diagnostic does not alter the opening vector. Do not imply that the original input or true historical rate can be recovered. If a value is missing, non-finite, or cannot be represented in the group's minor unit, require manual review. The opening balance preview must show the v3 displayed balances beside the proposed v4 balances, call out removed members and rounding differences, and require explicit confirmation of the final zero-sum vector. No silent adjustment to make it sum to zero.

V3 filters an old expense's participants against the **current** member roster, so a removed member may already have shifted historical debt in the proposed balance vector. Flag **every** legacy expense whose recorded split contains a now-removed member; show its stored amount, original split, and the v3-effective split, plus the balance effect of each. Require review of these rows and an explicit corrected opening vector before confirmation. If the original split is missing or ambiguous, flag it too. Never imply that the v3 displayed balance is historically exact.

Map each distinct v3 name to a stable v4 member ID derived from the old group ID and the **exact** name bytes. V3 could not distinguish two people with the same name; v4 cannot invent that distinction. Show the mapping for confirmation and require a manual rename or new group if it is ambiguous. Include historical names from payer and split fields even if no longer active. The old Yjs map's current currency is the proposed v4 settlement currency; compare it with the old `INIT` event and stop for manual review if they differ. Once confirmed, lock that currency in v4's `CREATE_GROUP` event.

For ordinary migration, compute a **semantic source digest**: SHA-256 of canonical JSON containing the v3 group's ID, name, currency, initial member-name list, and the full raw event multiset sorted by canonical event bytes, **excluding every `MIGRATED_TO_V4` marker**. Keep all other event fields, including old edits and voids. This digest remains stable when a marker is added or Yjs's binary encoding changes, but changes if the legacy group data changes. Store both the semantic digest and the separate binary archive digest with the v4 legacy archive.

Write a `MIGRATED_TO_V4` marker to the old Yjs room containing the target v4 room ID, **semantic** source digest, and marker ID. A second device that sees it follows that target and never auto-imports. If two devices start at once while disconnected or before seeing each other's marker, select the marker with the smallest ID after merge; only its target is active. Any other target is an orphan that must not be shared. The winning target contains one `LEGACY_OPENING` event whose ID is derived from the old group ID; identical retries are deduplicated. If different opening contents claim that ID, quarantine the collision and require manual reconciliation. Without an atomic server-side claim, concurrent creation cannot be prevented absolutely; the procedure prevents **silent** double migration and makes the active target deterministic. Recompute the semantic digest to detect later v3 changes and stop with a “v3 changed after migration” warning; never silently merge those late edits into v4. **If the old link may have leaked, do not write this marker**: export the old room, create a fresh unlinked v4 group with a random ID, and share its link privately.

## Storage for the first release

Liveblocks holds the shared Yjs document; IndexedDB holds each device's local copy. No AWS service is required for the initial implementation. The event schema, archive format, and storage adapter above are the migration boundary. Liveblocks free usage is a pilot limit, not a million-user capacity claim. [Liveblocks free limits](https://liveblocks.io/docs/pricing/plans/free). AWS backup and replacement options live in [LATER_AWS.md](LATER_AWS.md).

## Implementation gates for another agent

1. Freeze the event schema, canonicalization, collision behavior, correction winner, revision-bound rate rule, pending-reference rule, member lock, metadata policy, and FX status above. Then write a small pure ledger module and property-based tests for rounding, conservation, duplicates, replay order, corrections, membership races, stale rates, provisional totals, and currency minor units. Preserve the payer-friendly rounding rule exactly.
2. Make the app installable with a manifest, icons, HTTPS, and an actual service worker. Test installation, then launch from the home-screen icon and cold reopen a previously visited group with all network access disabled, including the JavaScript imports.
3. Adapt v3's Liveblocks/Yjs storage to the versioned event schema and adapter contract. Test both reconnect orders, local/remote collisions, remote event deletion and restoration from the local archive, read-back acknowledgement, and the actual 30-day field test above.
4. Simplify the UI while preserving the main trip flow. Test on a throttled 100 kbit/s connection and a small phone.
5. Implement full raw export/import and the explicit v3 migration above. Test old voids and edits, missing rates, removed-member split drift, duplicate names, two concurrent migration attempts, marker-excluded semantic digests, late v3 writes, and a leaked-link migration with no marker. Never replace an old room in place.
6. Run a pilot and measure room size, bandwidth, sync errors, and cost. The target of 100 to 1,000,000 people is a scaling objective; it needs a concrete active-user and group-usage model before capacity or cost can be claimed.
